01

Read-only by default

Agent and generated SQL run read-only, enforced by a SQL guard. Dangerous functions are blocked. MCP agents never receive database credentials.

02

Writes need a role and a confirm

Writes and DDL are permissions you grant per role. Every write needs a two-step confirm. DROP and TRUNCATE are blocked over MCP.

EXECUTE_WRITES · EXECUTE_DDL
03

Know who ran what

A per-user audit log, kept for 90 days. Every statement is tagged with the user who ran it. Role-based access and Google SSO.

04

Protected columns stay protected

Mark sensitive columns per connection. DeepSQL blocks queries that touch them.

05

Risky DDL flagged first

Schema Guardian flags risky schema changes before they ship. Lock timeouts and online ALTER keep busy tables safe.

Where does DeepSQL run?

Inside your own infrastructure: a Linux box, an EC2 instance or a container in your VPC. Database credentials stay in an AES-GCM encrypted vault.

Which databases does it guard?

PostgreSQL and MySQL, including databases behind a bastion over an SSH tunnel.

Which models can it use?

Yours. OpenAI, Azure OpenAI, Anthropic, a LiteLLM proxy, or a model on your own hardware through an OpenAI-compatible endpoint.

Do agents get database credentials?

No. MCP agents call DeepSQL, and DeepSQL holds the connection. Writes need a role and a two-step confirm.
